# client-sites

A dashboard plus one folder per client site. Read `README.md` for the workflow;
this file is the set of rules that keep the repo working.

## The shape

```
dashboard/                     the main Next.js app (App Router, src/app/)
sites/<category>/<project>/    one standalone Next.js app per client site
tools/*.mjs                    plain Node, zero dependencies, build-time only
_site/                         build output (gitignored) — what gets published
releases/                      client handovers (gitignored)
```

`sites/` is **exactly two levels deep**. A folder that is a Next.js app is a
project; a folder containing projects is a category. Nothing is registered
anywhere — `tools/projects.mjs` discovers them.

## Rules

**Every project is standalone.** A project must never import from outside its
own folder, and there is no shared UI package. Delivery is "copy the folder out,
`npm install`, `npm run build`", and anything shared would break that. Duplication
between projects is the intended trade.

**Never hardcode `basePath`.** Read it from the environment:

```ts
const basePath = process.env.NEXT_PUBLIC_BASE_PATH || "";
```

`tools/build.mjs` sets it to `<base prefix>/<category>/<project>` so the project
lands under the dashboard; `tools/release.mjs` leaves it unset so the client's
copy works at their domain root. `npm run check` fails on a hardcoded one,
because the symptom (a client's site loading with no CSS) appears far from the
cause.

**Every project needs `output: "export"`, `trailingSlash: true` and
`images: { unoptimized: true }`.** Without the first there is nothing to
publish; the other two keep the export portable across static hosts.

**Local assets need the prefix.** `<Image src="/photo.jpg">` does not get
`basePath` applied automatically — either prefix it with
`process.env.NEXT_PUBLIC_BASE_PATH` or keep images remote. The current templates
use remote images, so this has not come up yet.

**Copy templates, don't abstract them.** `npm run new -- <category>/<project>
--from <existing>` copies a project. A copy cannot break a site that is already
live; a shared template can.

## What not to bring back

This repo used to render sites from `site.json` files through a shared HTML
template, with hand-written `index.html` dashboards. All of it is gone: the
projects are Next.js apps, and the dashboard is one too. Do not add a
`site.json` renderer, a `sites/*/index.html` copied verbatim, or a second
definition of what counts as a project.

## Commands

```bash
npm run build                          # dashboard + every project -> _site/
npm run build car-wash/x               # one project
npm run preview                        # serve _site/ as it will be published
npm run dev                            # dashboard with hot reload
npm run list                           # what exists, plus structural problems
npm run check                          # pass/fail version of the above (CI)
npm run new -- <cat>/<proj> --from <cat>/<proj>
npm run release -- <cat>/<proj>        # standalone build for the client
```

To work on a site itself, use its own dev server:
`cd sites/<category>/<project> && npm run dev`.

## Next.js version

Next 16 with the App Router. Each project's `AGENTS.md` is generated by
`next dev` and points at `node_modules/next/dist/docs/` — read those docs rather
than relying on memory, since this version has breaking changes. Keep the Next
version the same across the dashboard and the projects.

## Things that will bite

- The dashboard is a static export, so it cannot read the filesystem. The
  project list is generated into `dashboard/src/generated/projects.json` and is
  committed; `tools/build.mjs` and `tools/dev.mjs` regenerate it, and CI checks
  it is current.
- A category folder must not share a name with a dashboard route (`about`,
  `privacy`, `_next`). The build stops if one does.
- `.build-stamp.json` beside a project records the base path its `out/` was
  built for, so an export made for one path is never republished under another.
  Delete it, or pass `--force`, to force a rebuild.
- **Never add a `package-lock.json` at the repo root.** Next infers its
  workspace root from the nearest lockfile; a root one makes every project
  resolve the repo root instead of itself, with a warning on every `next dev`.
  The root `package.json` has no dependencies, so it needs no lockfile.
- **Git Bash rewrites env vars that look like paths.** `NEXT_PUBLIC_BASE_PATH=/x
  npm run build` becomes `C:/Program Files/Git/x`. Prefix the command with
  `MSYS_NO_PATHCONV=1`, or use the tools — they pass the variable through Node,
  which is unaffected.
- Next writes a nested route's prefetch payload as a directory but requests it
  as a flat dotted file, so every prefetch 404s and navigation degrades to a
  full page load. `flattenPrefetchPayloads` in `tools/fsx.mjs` writes the flat
  name alongside it after each export; delete it once Next does this itself.
